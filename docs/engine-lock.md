# 引擎锁：同一个数据目录只由一个 MacBox 管理

同一个数据目录同一时间只有一个 MacBox 进程管理盒子：它持有 `engine.lock`，只有它能做启动收尾、运行守卫、借出偏好设置、给 App 上锁解锁、改动盒子。别的 MacBox 进程什么都不碰，只说明情况、转交打开请求。

## 1. 为什么只能有一个管理者

好几样关键状态只在管理盒子的那个进程的内存里，第二个进程看不到：

| 状态 | 在哪里 | 第二个进程会怎样 |
| --- | --- | --- |
| 运行中的会话 | `EscapeGuard` 的内存（[EscapeGuard.swift:126](../Sources/MacBox/Isolation/EscapeGuard.swift#L126)） | 它的守卫不认识第一个进程启动的 App，当成逃逸进程，50ms 内结束 |
| 启动收尾第 1 步 | `BoxStore.recoverInterruptedSessions` | 一启动就 SIGKILL 所有盒子进程：正在运行的应用被强制结束，没存的内容丢失 |
| 启动收尾第 3 步 | 同上 | 看到 `.lease.json` 就收回：正在运行的应用的设置被换回本机，它之后写的设置落进你真实的偏好设置 |
| 启动收尾第 7 步 | 同上 | 给所有 App 上锁：正在运行的应用再启动辅助程序会失败 |
| `Box.activity` | 内存 | 两边都以为盒子空闲，可以同时打开、同时还原 |
| 虚拟 Mac | `AppPaths.virtualMac` | 两个进程可以同时启动同一台虚拟机、写同一块磁盘 |

在引擎锁之前，没有任何单实例保护。LaunchServices 一般不会给同一个 bundle id 开第二个实例，但 `open -n`、直接运行 `build/MacBox.app` 里的二进制、打开另一份拷贝（比如 `~/MacBox-Backups` 里的旧版），都会开出第二个实例。

## 2. 怎么做的

- 文件 `<AppPaths.root>/engine.lock`：`open(O_RDWR | O_CREAT | O_NOFOLLOW | O_CLOEXEC, 0600)`，再 `flock(LOCK_EX | LOCK_NB)`，一直持有到进程结束（[EngineLock.swift](../Sources/MacBox/Core/EngineLock.swift)）。
  - 进程退出时（包括崩溃、被强制结束）内核自动释放，不会留下过期的锁。
  - 必须带 `O_CLOEXEC`：盒子里的程序要是继承了这个描述符，MacBox 崩溃后锁还被它们占着，下次就启动不了。
- 文件内容是拿着锁的进程（pid、App 路径、版本），只用来告诉用户是哪个 MacBox；谁是管理者只看 flock。
- `BoxStore.start()` 第一件事就是拿锁，拿到了才读盒子、启动守卫、做收尾。拿不到时什么都不碰（`BoxStore.ownership`）：
  - 窗口只显示“另一个 MacBox 正在管理这些盒子”，可以切过去或者退出（`NotManagingView`）；
  - 收到的打开请求（聚焦里的启动器、拖到程序坞图标上的安装包）转给正在管理盒子的那个 MacBox，然后退出。转给谁按锁文件里的 pid 问系统，要是正在运行的 MacBox，不信文件里写的路径。转不了的（两个是同一个 App 包时 LaunchServices 分不清该交给哪个实例，或者那个进程已经不是 MacBox）在说明页面上列出来，说它们没有处理。
- 同一个进程里重复拿锁，得到的是同一把锁（测试会在一个进程里先后建好几个 `BoxStore`）；同一个目录换个写法也一样（按真实路径算）。
- 锁文件建不了、打不开时（以前用 sudo 运行过、被换成了链接等）也不管理盒子：照旧管理的话，两个 MacBox 又会互相结束对方打开的应用。说明页面说清楚是哪个文件、为什么打不开，可以在访达中显示它，删掉后重新打开 MacBox 就好。
- 锁跟着数据目录走：`MACBOX_DATA_ROOT` 不同，锁也不同，测试实例和真实实例照样互不影响。
- 0.4.0 及更早的版本不拿锁。所以只有两边都是新版时才互相挡得住：发版后要尽快替换 /Applications 里的那份。

## 3. 测试

- [EngineLockTests.swift](../Tests/MacBoxTests/EngineLockTests.swift)：另一个进程拿着锁时拿不到，并读出是谁拿着；那个进程被 SIGKILL 后马上能拿到；同一个进程重复拿到的是同一把锁，换个写法的路径也是；描述符不会被子进程继承；锁文件打不开时不管理；`BoxStore` 拿不到锁时不读盒子、不做收尾，盒子里正在运行的程序不会被结束；转交打开请求的判断。
- 真实界面用 computer-use 驱动测试实例：在 `MACBOX_DATA_ROOT` 下先开一个，再用 `open -n` 开第二个，看说明页面和转交。

## 4. 命令行工具（暂停）

2026-10-28 做过一版 `macbox` 命令行工具：MacBox.app 当引擎，命令行经数据目录里的 Unix 套接字请它做事，MacBox 没开时先在后台把它打开。这版暂停了，代码留在 `cli-draft` 分支上，没有合进来。

暂停的原因：命令行要替用户在后台打开 MacBox，命令跑完了 MacBox 还留着。这和 MacBox 不留后台、不做用户没要求的事的原则相反，也不是常见工具那种命令行和 App 各自能用的样子。

应用在盒子里运行期间，必须有一个进程一直在场：守卫盯着逃出沙盒的进程，退出时收回借出的设置、把 App 重新上锁。所以以后要是再做命令行，应该是这样：

- 永远不替用户打开 MacBox。
- MacBox 开着时，请它去做。
- MacBox 没开时，命令行自己拿引擎锁，在前台管这个盒子，直到应用退出（终端一直占着，按 Ctrl-C 结束）。

这要先把核心从 App 里拆成库（架构评审时搁置的 BoxStore 拆分），引擎锁保证命令行和 App 不会同时管理。
